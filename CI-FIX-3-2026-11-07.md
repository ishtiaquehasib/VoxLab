# CI Fix 3 — v1.1.11 + v1.1.12 CI failures (2026-11-07, v1.1.13)

Both v1.1.11 (runs 42336764073 Linux / 42336764075 Windows) and v1.1.12
(runs 42337258768 Linux / 42337258784 Windows) CI failed. Two
independent causes, both fixed in v1.1.13.

## FAILURE 1 — Linux: `import qwen_tts` fails in "Verify faster-whisper installed"

CI error:

```
ModuleNotFoundError: No module named 'qwen_tts.core.configuration_qwen3_tts'
  raised from qwen_tts/core/__init__.py line 16:
  `from .configuration_qwen3_tts import Qwen3TTSConfig`
```

### Root cause — the browser web-upload SWAPPED two files (not bad code)

* The vendored code in local staging was CORRECT: `import qwen_tts`
  passes from the repo root in a clean venv (torch 2.6.0 /
  transformers 5.2.0, no pip qwen-tts installed — re-verified for
  v1.1.13, see below).
* Proven by diffing the live GitHub tree against staging
  (raw.githubusercontent.com vs the v1.1.12 staging copy, all 22
  qwen_tts files):
  * `qwen_tts/core/__init__.py` on GitHub (807 B) contains the
    MODELS content (`from .configuration_qwen3_tts import ...`);
    staging has the tokenizer content there (990 B).
  * `qwen_tts/core/models/__init__.py` on GitHub (990 B) contains
    the CORE content (tokenizer imports); staging has the
    config/model/processor content there (807 B).
  * The two `__init__.py` files were SWAPPED during the v1.1.11
    browser upload (same filename, similar size — the upload agent
    had even asked which was which and was given the right paths).
  * Same upload also misplaced the demo: `qwen_tts/demo.py` exists
    on GitHub (extra file) while `qwen_tts/cli/demo.py` is missing
    there; staging has it correctly at `qwen_tts/cli/demo.py`.
  * All other 20 qwen_tts files are byte-identical GitHub vs staging.
* Why the previous agent's check missed it: it verified the LOCAL
  staging copy only, which was correct. Nothing verified what
  actually landed on GitHub. The swap was invisible until CI
  imported the uploaded tree.

### Fix (v1.1.13)

* Staging files are the correct ones (re-asserted, not changed in
  substance) — BUT the re-upload must place them at the right paths.
  To make a repeat swap obvious and loud:
  * Both `__init__.py` files now carry a header comment naming
    their own path and role, and warning not to swap them.
  * New `qwen_tts/cli/__init__.py` package marker (upstream ships
    cli as a package; without it the demo is only a namespace
    package and `--collect-all` may skip it).
  * NEW CI step "Verify qwen_tts layout (v1.1.13 upload-swap
    guard)" in ALL THREE workflows, running BEFORE the import
    check: greps that `core/__init__.py` exports the tokenizers
    and `core/models/__init__.py` imports `configuration_qwen3_tts`
    (and not vice versa), that `qwen_tts/cli/demo.py` exists, and
    that no stray `qwen_tts/demo.py` exists. Fails with a readable
    `LAYOUT ERROR` instead of a cryptic import traceback.
  * The import check itself is strengthened to
    `from qwen_tts import Qwen3TTSModel, Qwen3TTSTokenizer`
    (was: bare `import qwen_tts`).
  * `qwen_tts/VENDORED.md` gains a "Layout — do not swap" section
    documenting both files' roles, sizes, and the failure.
* PARENT UPLOAD NOTE (browser, as ishtiaquehasib only): upload the
  two `__init__.py` files to their exact paths and verify each by
  its first import line; upload `qwen_tts/cli/demo.py` AND the new
  `qwen_tts/cli/__init__.py`; and DELETE the stray `qwen_tts/demo.py`

## FAILURE 2 — Windows: PowerShell ParserError in "Build with PyInstaller"

CI error: `ParserError ... "Missing expression after unary operator '--'"`
at the `--collect-all chatterbox` line.

### Root cause

The v1.1.11 edit appended trailing `# ...` comments AFTER the
PowerShell backtick line-continuations:

```
--collect-all qwen_tts ` # v1.1.11: vendored qwen_tts ...
--collect-all chatterbox ` # v1.1.11: explicit collect ...
```

In PowerShell a backtick-newline is the continuation; anything after
the backtick on the same line is parsed as code, so `# ...` is not a
comment there and `--collect-all` is read as a unary `--` operator.
The same two lines in the Linux/macOS workflows had the identical
trailing comment after a bash `\` continuation (also broken there —
bash treats the next line as a new command — it just failed on
Windows first).

### Fix (v1.1.13)

* Removed ALL trailing comments after line-continuations in ALL
  THREE workflows (6 lines total: 2 per workflow). The
  `--collect-all qwen_tts` and `--collect-all chatterbox` arguments
  themselves are unchanged.
* The explanation now lives as plain `#` YAML comment lines ABOVE
  the Build step (never inside the continued command — a comment
  line in the middle of a continued command would break the chain
  in both PowerShell and bash).
* Grep-verified: no line in any workflow ends a `\` or `` ` ``
  continuation with a trailing `#` comment.
